# 0001. 宣言ファイルの形式

- 状態：承認済み
- 日付：2026-09-30

## 背景

diskform は、一つの宣言ファイルからストレージの構成を組み立てます。
AGENTS.md 7 章では、その宣言ファイルの形式が未確定（TBD）になっていました。

形式を選ぶうえで、次の点を考慮しました。

- 宣言は、別の宣言要素への参照（パーティション、LUKS、VG など）を多く含みます。
- 宣言の誤りは、誤ったデバイスの操作につながりえます。
  そのため、未定義の値や型の食い違いを、推測で補わずにエラーにできる必要があります。
- 利用者は、エディタでの補完や検証、スクリプトでの加工といった周辺ツールを使えることを期待します。

## 判断

宣言ファイルは YAML と JSON に対応します。

- 両形式を同じ型に読み込み、以後の検証と計画は形式に依存しないようにします。
- 形式は拡張子（`.yaml`、`.yml`、`.json`）で判別します。
  中身から形式を推測することはしません。
  それ以外の拡張子はエラーにします。
- テンプレートの展開（変数の埋め込み、条件分岐、繰り返し）はしません。
  ホストごとに異なる宣言が必要な場合は、外部のツールで YAML か JSON を生成してもらいます。
- 期待する型と異なる値は、暗黙に変換せずにエラーにします。
  たとえば、文字列を期待する項目に数値が書かれていたら、文字列に変換せずに拒否します。

## 検討した代替案

### HCL

HCL では、参照を文字列ではなく式として書けます。
ブロックの入れ子と参照のパスが一致し、参照とデバイスのパスを構文の段階で区別できる利点がありました。

採らなかった理由は二つあります。
一つは、YAML と JSON に比べて周辺ツール（JSON Schema によるエディタの補完と検証、yq による加工）が乏しいことです。
もう一つは、Terraform の経験がある利用者が、変数、モジュール、state があると期待しやすいことです。
diskform はこれらを持たないので、期待との食い違いを生みます。

### YAML と minijinja によるテンプレート

YAML をテンプレートとして展開すれば、ホストごとの違いを一つのファイルで表現できます。

採らなかった理由は、テキストのテンプレートが安全性の問題を持ち込むことです。
既定の設定では、未定義の変数が空文字列に展開されます。
たとえば対象ディスクのシリアルを渡し忘れると、照合条件が空になり、実装によっては意図しないディスクに一致する可能性があります。
また、値をそのまま埋め込むと型が変わることがあります（先頭にゼロを持つシリアルが数値として読まれる、など）。
これらは制約を設ければ避けられますが、テンプレートを必要とする例がまだないので、機能ごと見送ります。

## 制約

- 参照は文字列で書くので、参照の文法を定め、パーサーとは別に検証する必要があります。
  参照の文法は、宣言の構造とあわせて別途決めます。
- YAML のパーサーの選定は、実装の時点で行います。
- テンプレートを必要とする例が現れたら、この判断を見直します。
