# 0004. コマンド体系

- 状態：承認済み
- 日付：2026-09-30

## 背景

diskform は、宣言の検証、計画、ストレージの変更を行います。
AGENTS.md 3 章は、構成の解析とストレージの変更を分離すること、計画の段階ではデバイスを変更しないこと、破壊的な操作には明示的な許可を必要とすることを求めています。

これらの段階を、どのサブコマンドに分け、利用者の許可をどう受け取るかを決める必要がありました。
将来、Secure Erase のような消去の手段を加える可能性も考慮しました。

## 判断

### サブコマンド

サブコマンドは次の六つです。

- **`validate`**：宣言を解析し、型、参照、サイズの計算規則を検証します。デバイスには一切アクセスしません。
- **`plan`**：`validate` の検証に加え、ADR 0003 の照合でデバイスを解決し、実行する予定の操作と警告を表示します。デバイスの状態を読みますが、変更はしません。
- **`apply`**：宣言の構成を作ります。既存のデータは消しません。
- **`destroy`**：指定されたディスクの既存のデータを消去します。
- **`mount`**：構成済みのストレージをマウントします。
- **`unmount`**：マウントを解除します。

どのサブコマンドも、宣言ファイルを位置引数で受け取ります。
既定のファイル名は設けません。

### apply

`apply` は、実行のたびに計画を作り直します。
計画をファイルに保存して後から実行する機能は設けません。

`apply` は、既存の署名（パーティションテーブル、LUKS ヘッダ、ファイルシステムなど）があるディスクには書き込まず、拒否します。
ただし、既存の構成がすでに宣言を満たしている場合は、何も変更せずに成功します。
（この判定の方法と単位は、ADR 0011 で決めました。）
既存のデータを消す必要がある場合、利用者は先に `destroy` を実行します。

### destroy

`destroy` は、消去の対象を次のどちらかで指定させます。

- **`--target`**：宣言の中の名前でディスクを指定します（`--target disk.data0` など）。複数回指定できます。
- **`--all`**：宣言のすべてのディスクを対象にします。

どちらかの指定は必須で、どちらも指定しなければエラーにします。
両方を指定した場合も、エラーにします。
対象として指定できるのは、ディスクの単位です。
対象にしなかったディスクには触れません。

#### 複数のディスクにまたがる構成

複数のディスクにまたがる構成（btrfs の複数デバイス構成、md のアレイ、複数の PV を持つ VG）について、次の二つを検査します。
メンバーの判定には、宣言ではなく、実際のデバイスの状態を使います。

一つ目は、宣言の完全さです。
宣言のディスクにある構成のメンバーが、このマシンの他のディスクにあり、そのディスクが宣言に含まれていなければ、拒否します。
拒否するときは、そのディスクのパスを示します。
このマシンに存在しないメンバー（他の筐体から一部のディスクだけを流用した場合など）は、拒否の理由にしません。
欠けているメンバーがあることを、確認のときに示します。

二つ目は、対象の過不足です。
`--target` で指定したディスクにある構成のメンバーが、このマシンの対象外のディスクにあれば、拒否します。
一部のメンバーだけを消去すると、残りのディスクに欠けた構成が残るためです。
拒否するときは、追加で指定すべきディスクを示します。
一つ目の検査により、そのディスクは必ず宣言に含まれているので、利用者は `--target` を追加するか `--all` を使えば対象にできます。

#### 使用中のデバイス

対象ディスクの配下に、マウントされたファイルシステムか有効な swap がある場合は、拒否します。
利用者は、必要なら先に `unmount` を実行します。

それ以外の使用中の状態（開いている LUKS のマッピング、稼働中の md のアレイ、活性化された VG）は、それが対象ディスク上の構成だけから成る場合に限り、`destroy` が上の層から順に解除してから消去します。
解除する対象は、確認のときに示します。
対象ディスクの外のデバイスが関わる場合や、種類を判別できない device-mapper の参照がある場合は、拒否します。

この解除を設ける理由は、他の筐体から流用したディスクでは、udev の規則によって md のアレイの組み立てや VG の活性化が自動で行われることがあるためです。
これらは宣言にない構成なので、`unmount` では解除できません。
（ADR 0016 で、md のアレイの解除は、md を使う例が現れるまで実装せず、拒否することにしました。）

#### 消去の範囲

`destroy` は、対象ディスクの既存の構成を、配下から順に消去します。

1. ディスク上の各パーティションについて、署名（LUKS ヘッダ、md のスーパーブロック、LVM の PV ラベル、ファイルシステムの署名など）を消去します。
2. ディスク全体に直接書かれた署名と、パーティションテーブルを消去します。
   GPT の場合は、先頭と末尾の両方のテーブルを消去します。

消去の対象は、宣言にあるパーティションではなく、実際にディスク上にあるパーティションです。
そのため、以前の構成が分からないディスク（他の筐体から流用したディスクなど）も、宣言で照合できれば消去できます。

パーティションテーブルだけを消去しない理由は、古い署名がパーティションの中に残るためです。
同じレイアウトでパーティションを作り直すと、古い LUKS ヘッダやファイルシステムが同じ位置に現れます。
`apply` がそれを「すでに構成済み」と誤って判定する可能性があります。

`destroy` の消去は、署名を消して既存の構成を認識されなくする操作です。
データを復元できなくすることは保証しません。
その保証が必要な消去（Secure Erase など）を加える場合は、別のサブコマンドにします。

### 確認

`apply` と `destroy` は、実行する予定の操作を表示し、利用者の確認を得てから実行します。
`--auto-approve` を付けると、確認を省きます。

- `--auto-approve` が省くのは確認だけです。照合の検証、使用中のデバイスの検出、実行直前の再検証は省きません。
- 標準入力が端末でなく、`--auto-approve` も付いていない場合は、確認を待たずに拒否します。

### mount と unmount

マウントとその解除は、`apply` から分けます。
これにより、構成済みのストレージを、再インストールや復旧のためにマウントするだけの操作ができます。
また、`destroy` の前に使用中の状態を解除する手段にもなります。

`mount` は、宣言の構成を下の層から順に使用可能にします。
LUKS を開き、VG を活性化し、ファイルシステムを `--root` で指定したディレクトリの下にマウントします。
`--root` は必須で、既定値は設けません。
既定値があると、指定を忘れたときに意図しない場所（`/` など）にマウントするためです。
swap は有効にしません。
インストール中の環境で、インストール先の swap を有効にする必要はないからです。

`unmount` は、`mount` の逆順に、ファイルシステムのアンマウント、VG の非活性化、LUKS のマッピングを閉じる操作を行います。
対象は宣言にある構成だけです。

fstab や crypttab のような、起動後のマウントのための設定は生成しません。

## 検討した代替案

### 破壊を apply のオプションにする

`apply --wipe` のように、`apply` に既存のデータを消す許可を渡す案です。
採らなかったのは、`apply` が既存のデータを消すかどうかがオプションで変わると、`apply` の契約が単純でなくなるためです。
また、Secure Erase のような消去の手段を加えるときも、`apply` のオプションより、別のサブコマンドのほうが扱いやすくなります。

### 宣言に破壊の許可を書く

宣言に `wipe: true` のような項目を書く案です。
宣言は保存されて使い回されるので、許可も一緒に使い回されてしまいます。
`destroy` で対象を都度指定させるほうが、実行のたびに人間が対象を選ぶことになります。

### apply を format と呼ぶ

disko のモード名（destroy、format、mount）と揃います。
しかし「フォーマット」は、既存のデータを消して初期化する意味で使われることが多く、既存の署名を拒否する挙動と食い違います。
また、構成済みのディスクに再実行して何もしない挙動も、`format` という名前からは予想しにくくなります。

### 確認を省くオプションの名前

`--force` は、確認以外の安全チェックも省くと読まれやすいので採りませんでした。
`--yes` と `--approved` も検討しました。
Terraform の `apply` と `destroy` に同じ意味の慣例があるので、`--auto-approve` を選びました。

### 計画をファイルに保存する

Terraform の `plan -out` のように、計画を保存して `apply` に渡す案です。
AGENTS.md 3 章は、以前に作った計画が実行時もそのまま有効だとは仮定しないことを求めています。
保存した計画を使っても、実行時に状態を検証し直す必要があるので、計画を毎回作り直すほうが単純です。

### 対象を省略したら宣言のすべてのディスクを消去する

Terraform の `destroy` と同じく、既定で全部を対象にし、`--target` で絞る案です。
採らなかったのは、`--auto-approve` と組み合わせると、対象の指定を忘れただけで、データディスクを含むすべてのディスクが確認なしに消去されるためです。
全部を消去するときも `--all` の一語で済むので、指定の手間はほとんど増えません。

### またがる構成のメンバーを自動で対象に加える

`--target` で指定したディスクと構成を共有するディスクを、自動で対象に加える案です。
指定の手間は減りますが、指定していないディスクが消去されることになります。
`--auto-approve` を付けると、利用者は加えられたディスクを確認しないまま消去します。
拒否して追加で指定すべきディスクを示すほうが、消去されるディスクが常に利用者の指定と一致します。

### またがる構成の一部だけの消去を許す

`--target` で指定されていれば、構成の一部だけでも消去し、警告にとどめる案です。
一部だけを消去すると、残りのディスクには欠けた構成と既存の署名が残ります。
そのディスクには `apply` できないので、結局はそのディスクも消去することになります。
一部だけの消去を必要とする例もないので、拒否することにしました。

### destroy でマウントも自動で解除する

disko の destroy は、ファイルシステムをアンマウントしてから消去します。
採らなかったのは、AGENTS.md 3 章が、変更の前に対象が使用中でないことを確認するよう求めているためです。
マウントされたファイルシステムや有効な swap は、利用者が使っている可能性があります。
自動で解除すると、利用者が使用中だと気付かないまま消去が進みます。
自動で解除するのは、マウントされていない LUKS、md、VG の層に限りました。

### 使用中の状態をすべて拒否する

`destroy` は使用中の状態を一切解除せず、利用者に解除させる案です。
他の筐体から流用したディスクでは、自動で組み立てられた md や活性化された VG が宣言にないため、利用者は `mdadm` や `vgchange` を手で実行する必要があります。
同じ機種のマシンに大量に展開する用途では、この手作業が手順の妨げになります。

### mount の既定のルートを /mnt にする

disko は、既定で `/mnt` の下にマウントします。
既定値を設けると、指定を忘れても動いてしまうので、`--root` を必須にしました。

### validate を plan に含める

`plan` だけでも宣言の誤りは検出できます。
しかし `plan` はデバイスの状態を読むので、対象のマシンがない環境（CI など）では実行できません。
デバイスにアクセスしない `validate` を分けておけば、そうした環境でも宣言を検証できます。

## 制約

- 自動化された環境で `apply` や `destroy` を実行するには、`--auto-approve` が必要です。
- 複数のディスクにまたがる構成を持つディスクを消去するには、そのメンバーのディスクをすべて宣言に含め、すべてを対象にする必要があります。
- `apply` は計画を作り直すので、直前に実行した `plan` の結果と異なる場合があります。
  利用者は、`apply` が表示する計画を確認する必要があります。
- 起動後のマウントの設定（fstab、crypttab）が必要な例が現れたら、生成の要否を見直します。
