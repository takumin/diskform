# 0007. validate で検査する規則

- 状態：承認済み
- 日付：2026-10-02

## 背景

`validate` は、デバイスにアクセスせずに宣言を検証します（ADR 0004）。
検証の規則の多くは ADR 0002 と ADR 0005 で決めていますが、実装にあたって、次の点がまだ決まっていませんでした。

- 列挙的な値（パーティションテーブルの種類、ファイルシステムの形式など）として、何を受け付けるか。
- パスとして、どのような書き方を受け付けるか。
- ラベルの長さの上限を、形式ごとにいくつにするか（ADR 0005 は、上限を形式ごとに設けることだけを決めています）。
- 宣言だけから検出できる衝突（マウント先の重複など）を、どこまで検査するか。

AGENTS.md 2 章は、未定義の挙動を推測で埋めずに明示的なエラーにすることを求めています。
一方、仮想的なユースケースのための機能は実装しません。

## 判断

### 受け付ける値

列挙的な値は、例に現れたものだけを受け付けます。

- パーティションテーブル（`table`）：`gpt`
- partition の種類（`type`）：`esp`（省略もできます）
- ファイルシステムの形式（`format`）：`vfat`、`ext4`、`xfs`、`btrfs`
- btrfs のプロファイル（`data_profile`、`metadata_profile`）：`raid1`

それ以外の値は、未知の値としてエラーにします。
新しい値が必要な例が現れたら、その値の意味（作るときの挙動と、再適用のときの判定）を決めてから追加します。

btrfs のプロファイルには、必要なデバイスの数を検査します。
`raid1` には二つ以上のデバイスが必要です。

### サイズ

ADR 0002 の表記のうち、固定サイズの整数は正の整数に限ります。
`0GiB` は、作られる要素の大きさとして意味を持たないので拒否します。
符号と先頭のゼロ（`+1GiB`、`01GiB`、`050%`）も、表記を一つに保つために拒否します。

### パス

マウント先と鍵ファイル（`keyfile`）は、絶対パスに限ります。
相対パスは、基準（作業ディレクトリか、宣言ファイルの場所か）が決まらないので拒否します。

絶対パスは、正規形に限ります。
空の要素（`//`）、`.`、`..`、末尾のスラッシュを含むパスは拒否します。
同じ場所を指すパスの書き方を一つにして、マウント先の重複を文字列の比較で検出できるようにするためです。

ディスクの照合条件の `path` も、同じ正規形に限ります。
加えて、`/dev/` から始まること（ADR 0003）を検査し、`..` で `/dev/` の外を指すことを防ぎます。
ワイルドカードについては、最後の要素以外に現れないこと（ADR 0003）と、`[` と `]` が対応していることを検査します。

subvolume の `path` は、ファイルシステムの最上位からの相対パスで、同じ正規形に限ります。
同じファイルシステムの中で、二つの subvolume が同じ `path` を使う場合は拒否します。

### ラベル

ラベルの長さの上限は、次のとおりにします。

| 書き込む先 | 上限 |
| --- | --- |
| PARTLABEL | 36（UTF-16 の符号単位） |
| vfat | 11 バイト |
| ext4 | 16 バイト |
| xfs | 12 バイト |
| btrfs | 255 バイト |
| swap | 16 バイト |

バイト数は UTF-8 で数えます。
vfat のラベルはコードページで符号化されるので、ASCII 以外の文字を含むラベルでは、実際より厳しく判定することがあります。

ラベルには、制御文字を使えないことにします。
`/dev/disk/by-label/` の名前やツールの出力に、改行などがそのまま現れるのを避けるためです。

### 宣言の中の衝突

宣言だけから検出できる衝突として、次を拒否します。

- **マウント先の重複**：二つのファイルシステムまたは subvolume が、同じマウント先を使う場合です。
  後からマウントしたものが先のものを隠すので、どちらが見えるかがマウントの順序に依存します。
- **device-mapper の名前の衝突**：LUKS のマッピングと LV は、同じ device-mapper の名前空間に現れます。
  LV は、VG と LV の名前の `-` を `--` に置き換えて `-` でつないだ名前になります。
  たとえば、LUKS の `vg0-root` と、VG `vg0` の LV `root` は衝突します。
  この衝突は apply の途中で失敗を起こし、部分的に構成された状態を残すので、事前に拒否します。

### その他

- VG の `devices` と、ファイルシステムの `devices` は、空にできません。
- `mount_options` の各要素は、空の文字列にできません。
- 最上位の節（`disk`、`luks`、`lvm`、`filesystem`、`swap`）は、省略できます。省略した節は、要素を持たないものとして扱います。

## 検討した代替案

### 各ツールが受け付ける値をすべて受け付ける

たとえば btrfs のプロファイルとして、`mkfs.btrfs` が受け付ける `single`、`dup`、`raid0`、`raid10`、`raid5`、`raid6` なども受け付ける案です。
値ごとに必要なデバイスの数が異なり、再適用のときの判定も値ごとに確かめる必要があります。
例のない値について、その挙動を apply 層のテストで検証できないので、採りませんでした。

### ラベルの長さを文字数で数える

利用者には直感的です。
しかし、ext4 や xfs の上限はバイト数で決まっているので、ASCII 以外の文字を含むラベルが、validate を通っても作成時に失敗するか切り詰められることになります。

## 制約

- validate は、宣言だけで決まる規則しか検査しません。
  固定サイズの合計が親の容量を超えないか（ADR 0002）、二つの `disk` が同じデバイスに解決されないか（ADR 0003）、VG や LUKS の名前がシステムの既存のものと衝突しないか（ADR 0005）は、デバイスの状態を読む plan で検査します。
- 二つの `disk` の `path` が同じ文字列でも、validate では拒否しません。
  同じデバイスに解決されるかどうかは、plan で判定します。
- `partitions` が空のディスクは、validate では拒否しません。
  apply がそのディスクをどう扱うかは、apply の実装の時点で決めます。
- 受け付ける値を例に合わせて限っているので、例にない構成（MBR のディスク、BIOS boot のパーティション、raid1 以外の btrfs など）は、validate の時点で拒否されます。
