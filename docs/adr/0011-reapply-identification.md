# 0011. 再適用での同定と判定

- 状態：承認済み
- 日付：2026-10-03

## 背景

ADR 0004 は、`apply` が既存の署名のあるディスクに書き込まずに拒否し、既存の構成がすでに宣言を満たしている場合は何も変更せずに成功することを定めています。
この判定には、既存のパーティション、LUKS、VG、ファイルシステムが、宣言のどの要素に当たるかを決める方法（同定）が必要です。
ADR 0005 は、この方法を別に決めるとしていました。

判定を誤って「満たしている」とすると、宣言と異なる構成がそのまま使われます。
判定を誤って「空」とすると、既存のデータを上書きします。
そのため、判定はデータの保全に直接関わります。

## 判断

### 同定の方法

既存の構成は、宣言の構造をたどり、位置で宣言の要素に対応させます。
ディスクに目印を書き込む方法や、状態ファイルを持つ方法は採りません。

- **ディスク**：ADR 0003 の照合で対応させます。
- **パーティション**：パーティションの番号で、宣言の並びと対応させます。
- **LUKS**：参照先のデバイスの上にあるものを対応させます。
- **VG と LV**：宣言の名前がそのままシステム上の名前なので（ADR 0005）、名前で対応させます。
- **ファイルシステムと swap**：参照先のデバイスの上にあるものを対応させます。
- **subvolume**：`path` で対応させます。

### 判定の単位

判定は、参照でつながったディスクの組（以下、**組**）を単位にします。
二つのディスクは、その上の構成が一つの要素を共有するとき（同じ VG の PV や、同じ btrfs のデバイスを持つときなど）、同じ組に属します。
例では、システムディスクが一つの組、二台のデータディスクがもう一つの組になります。

組ごとに、次の三つのどれかに判定します。

- **空**：組のすべてのディスクに、パーティションテーブルも署名もありません。apply は、この組の構成を作ります。
- **構成済み**：組の構成全体が、次節の比較で宣言と一致します。apply は、この組を変更しません。
- **それ以外**：apply は拒否します。plan は、宣言と異なる点を示します。

一部のディスクだけが空の組、一部の層だけが作られた組（パーティションはあるが LUKS がないなど）は、「それ以外」に当たります。
つまり、部分的に失敗した apply の続きから再開することはしません。
利用者は、`destroy` で組を消去してから、apply をやり直します。
署名のないパーティションを空と見なさない理由は、blkid が検出できない形式のデータが残っている可能性があるからです。

組を単位にするので、データディスクの組を残したまま、システムディスクの組だけを `destroy` して作り直せます。

### 比べる項目

（各項目の読み取りの方法と比べ方は、ADR 0015 で決めました。）

「構成済み」とは、空のディスクに apply したのと同じ結果になっていることです。
次の項目を比べ、一つでも異なれば「それ以外」とします。

- **ディスク**：パーティションテーブルの種類。
- **パーティション**：数、GPT の種類、開始位置と大きさ（計算結果とアラインメントの単位以内の差、ADR 0002）、PARTLABEL。
- **LUKS**：LUKS2 のヘッダがあること、宣言の鍵ファイルで鍵スロットを開けること。
  鍵の照合は、マッピングを作らない検査（`cryptsetup open --test-passphrase`）で行います。
  開けない LUKS を構成済みとすると、`mount` で初めて失敗するためです。
- **VG**：PV の集合、PE のサイズ（ADR 0010）、LV の集合。宣言にない LV があれば、異なるものとします（ADR 0002）。
- **LV**：大きさ（計算結果と PE のサイズ以内の差、ADR 0002）。
- **ファイルシステム**：形式とラベル。btrfs では、加えてデバイスの集合と、データとメタデータのプロファイル。
- **subvolume**：宣言の `path` の subvolume があること。宣言にない subvolume があっても、異なるものとはしません。
  スナップショットの管理ツールなどが、運用中に subvolume を作るためです。
- **swap**：swap の署名とラベル。

ラベルは、宣言の文字列と等しいかで比べます。
宣言のラベルが空の場合は、既存のラベルがないことを要求します（ADR 0008）。

次の項目は比べません。

- UUID：宣言にない値です。
- LUKS の暗号方式と PBKDF（ADR 0009）：宣言にない値です。
- `mount_options`：作成ではなく、マウントのときだけに使う値です。
- どこからも参照されないパーティションの中身：宣言は、その中身について何も定めていません。

### 状態を変えずに読めない項目

plan はデバイスを変更しないので（ADR 0004）、比べる項目を読むために、LUKS を開いたり、ファイルシステムをマウントしたりしません。
LUKS を開くと、udev の規則によって中の VG が自動で活性化されることがあり、plan の後に状態が残るためです。

そのため、閉じている LUKS の上の層（例では VG、LV、ファイルシステム、swap）は、比べられません。
状態を変えずに読めない項目が残った組は、構成済みと判定せず、「それ以外」として拒否します。
plan は、比べられなかった項目と、その理由を示します。
LUKS がすでに開いている場合は、そのマッピングを通して上の層を比べます。

## 検討した代替案

### 目印を書き込む

PARTLABEL、パーティションの UUID、LUKS のトークンなどに、diskform の目印を書き込んで同定する案です。
宣言の名前から目印を導くと、同じ宣言で展開した別のマシンのディスクと区別できず、他の筐体から流用したディスクを自分の構成と誤認するおそれがあります。
また、`label` は宣言の値をそのまま書くので（ADR 0008）、目印に使えません。

### 状態ファイルを持つ

Terraform の state のように、作った構成を記録しておく案です。
ディスクは筐体の間で移されることがあり、状態ファイルとディスクの内容が一致する保証がありません。
結局、ディスクの内容を読んで確かめる必要があるので、状態ファイルは判定の根拠になりません。

### ディスクを単位にする

ディスクごとに、空か構成済みかを判定する案です。
複数のディスクにまたがる btrfs で、片方のディスクだけが空の場合、そのディスクだけに構成を作ることになります。
既存のファイルシステムへのデバイスの追加が必要になり、diskform はその操作をサポートしていません。

### 部分的な構成の続きから再開する

失敗した apply の後に、作られていない層だけを作る案です。
`destroy` を挟まずにやり直せます。
しかし、署名のないパーティションを空と見なして書き込むと、blkid が検出できない形式のデータを黙って消すおそれがあります。

### plan が LUKS を一時的に開く

閉じている LUKS の上の層も比べられます。
しかし、背景の理由で、plan の後にマッピングや活性化された VG が残るおそれがあります。

## 制約

- 閉じている LUKS を持つ組は、構成済みと判定できません。
  再適用で何もせずに成功させるには、利用者が先に LUKS を開いておく必要があります。
  `mount` を実装する時点で、この手順を見直します。
- 構成済みの組を運用中に変更した場合（LV の追加、ラベルの変更など）、apply はその組を拒否します。
- 判定は冪等性とデータの保全に関わるので、apply 層のテストで、空の組、構成済みの組、部分的に構成された組のそれぞれを検証する必要があります。
