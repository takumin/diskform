# 0013. plan 層のテストでのデバイスの状態

- 状態：承認済み
- 日付：2026-10-03

## 背景

AGENTS.md 5 章は、plan 層の受け入れテストを特権なしで常に実行し、物理ストレージデバイスへのアクセスを必要としないことを求めています。
一方、`plan` はデバイスの状態（ディスクの照合、容量、既存の署名、既存の VG の名前など）を読みます。
テストを実行するマシンのデバイスの状態は、マシンごとに異なり、特権なしでは読めないものもあります。

## 判断

`plan` は、デバイスの状態をすべて `System` トレイトを通して読みます。
実際のマシンを読む実装（`Host`）は、sysfs、`/dev`、blkid、vgs を使います。

plan 層のテストは、`System` の偽の実装を与えて、`plan` をライブラリの関数として呼び出します。
そのために、クレートをライブラリとバイナリに分けました。
偽の実装は、ディスク、シンボリックリンク、既存の署名、鍵ファイル、既存の名前を、テストごとに組み立てます。

`System` の操作は、読み取りだけです。
デバイスを変更する操作は、`System` に加えません。

## 検討した代替案

### バイナリに偽の状態を読み込ませる

環境変数などで偽の状態のファイルを指定し、バイナリを実行してテストする案です。
バイナリの外から観察できる挙動をそのまま検証できます。
しかし、実際のデバイスの代わりに偽の状態を読む経路が、配布するバイナリに残ります。
apply を実装したときに、その経路が誤って有効になると、計画と異なるデバイスを変更するおそれがあります。

### 偽の sysfs と /dev のディレクトリを用意する

読むパスの起点を差し替えて、ディレクトリの木で状態を表す案です。
blkid や vgs のような外部コマンドの結果は、ディレクトリの木では表せません。

## 制約

- `Host` の実装は、plan 層のテストでは検証されません。
  `Host` の検証は、apply 層のテストで行う必要があります。
  apply 層のテストの実行方法は、AGENTS.md 7 章でまだ決まっていません。
