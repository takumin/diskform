# 0017. apply 層のテストの実行環境

- 状態：承認済み
- 日付：2026-10-10

## 背景

AGENTS.md 5 章は、apply 層の受け入れテストを、ループデバイスや VM などの隔離した環境で実行することを求めています。
AGENTS.md 7 章は、その実行方法（必要な権限と環境）をメンテナーが決める項目にしていました。

apply 層のテストは、device-mapper、dm-crypt、btrfs のようなカーネルの機能と、cryptsetup、lvm2、btrfs-progs のようなツールを必要とします。
これらがそろっているかは、テストを実行するマシンごとに異なります。
また、テストは root でデバイスを変更するので、テストの誤りが、テストを実行するマシンのデバイスを壊すおそれがあります。

ADR 0013 は、`Host` の実装（実際のマシンの読み取り）の検証を apply 層のテストに委ねています。
ADR 0016 の `destroy` も、LUKS の解除、VG の非活性化、マウントされた btrfs の検出を、実際のカーネルで確かめていませんでした。

## 判断

メンテナーの判断により、次のように決めました。

- apply 層のテストは、cloud-hypervisor の VM の中で実行します。
  CI でも手元でも、同じ VM で実行できるようにします。
- テストは、環境変数で有効にします。
- CI では、apply 層のテストに加えて、`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test` を実行します。

これを、次のように実装しました。

### 有効にする方法と、実行しなかったことの表示

環境変数 `DISKFORM_APPLY_VM` に、VM のファイルを置いたディレクトリを指定すると、テストを実行します。
そのディレクトリは、`tests/apply/fetch-vm.sh` で用意します。

環境変数を設定しない場合、テストのバイナリは、テストをスキップしたことを表示して成功で終わります。
cargo のテストの仕組み（libtest）には、テストを実行時にスキップする方法がありません。
libtest のまま環境変数で何もせずに戻ると、実行しなかったテストが成功として表示されます。
そのため、apply 層のテストは libtest を使わず（`harness = false`）、スキップしたことを自分で表示します。

環境変数を設定したのに、VM のファイルや `/dev/kvm` が使えない場合は、スキップせずに失敗します。

### VM の構成

VM は、Ubuntu 26.04 のクラウドイメージのカーネル、initrd、ルートファイルシステムで起動します。
取得するファイルは、版とハッシュを `tests/apply/fetch-vm.sh` に固定します。

- ルートファイルシステムのイメージは読み取り専用で接続し、その上に tmpfs を重ねます（dracut の `rd.overlay`）。
  テストがイメージを変えないので、すべてのテストが同じ初期状態から始まります。
- テストのバイナリと diskform のバイナリは、ホストで作る小さな ext4 のディスクで渡します。
- カーネルのコマンドラインの `systemd.run` で、テストを最小限の起動の後に実行し、終わったら電源を切ります。
  cloud-init は無効にします。
- テストの出力は virtio のコンソールに、カーネルと systemd の出力はシリアルコンソールに分けて、ホストのファイルに書きます。

テストごとに VM を一つ起動し、テストが宣言したシリアルと容量の空のディスクを与えます。
VM の中では、ディスクを udev が作る `/dev/disk/by-id/virtio-<serial>` で照合します。
テストの間でデバイスの状態を共有しないので、後片付けに失敗したテストが、次のテストに影響しません。

一つのテストのバイナリが、ホストでは VM を起動し、VM の中では `--guest <テストの名前>` で、そのテストを root で実行します。

## 検討した代替案

### GitHub Actions のランナーで、ループデバイスを使う

ランナーは使い捨ての VM なので、sudo でループデバイスを作ってテストできます。
準備は少なくて済みます。
しかし、手元で同じ環境を作れず、手元で実行するときにはテストが手元のマシンのデバイスを変更します。

### QEMU

同じように VM で隔離できます。
メンテナーの判断で、cloud-hypervisor を選びました。

### VM の中でループデバイスを使う

一つの VM で全テストを実行し、テストごとにループデバイスを作る案です。
起動が一度で済みます。
しかし、テストの間で LVM や LUKS の名前、マウントを共有するので、失敗したテストの後始末が次のテストに影響します。
また、照合の対象がカーネルの名前に限られ、例と同じ by-id による照合を検証できません。

### 専用のカーネルとルートファイルシステムを作る

カーネルを最小限の設定でビルドし、ルートファイルシステムも必要なツールだけで作る案です。
起動は速くなります。
しかし、ビルドの手順と時間がかかり、実際の配布物の構成からも離れます。

## 制約

- KVM が使えるマシンでしか実行できません。
  `/dev/kvm` を読み書きできる必要がありますが、root は必要ありません。
- 手元で実行するには、cloud-hypervisor を実行できる x86-64 の Linux と、ext4 のイメージを作る `mkfs.ext4`（`-d` に対応したもの）が必要です。
- テストのバイナリと diskform は、ホストでビルドしたものを VM の中で実行します。
  そのため、ホストの glibc が、VM の Ubuntu 26.04 の glibc（2.43）より新しいと、実行できない可能性があります。
- 最初の取得では、約 1 GB をダウンロードします。
- apply がまだないため、現在のテストは、例と同じ構成を通常のツールで作ってから `destroy` を検証します。
