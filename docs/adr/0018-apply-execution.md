# 0018. apply の実行

- 状態：承認済み
- 日付：2026-10-12

## 背景

ADR 0004 は、`apply` が既存の署名のあるディスクに書き込まないこと、確認を得てから実行すること、実行のたびに計画を作り直すことを定めています。
ADR 0011 は、ディスクの組ごとに、空なら作り、構成済みなら変更しないことを定めています。
ADR 0009 と ADR 0010 は、LUKS と LVM の作成パラメータを固定しています。

しかし、各操作をどの手段で行うか、操作の前後に何を確かめるか、作った後のデバイスをどの状態で残すか、途中で失敗した場合にどうするかは決めていません。

組が空であることは、ディスク自体にパーティションテーブルも署名もないことで判定します（ADR 0011、ADR 0015）。
この判定は、ディスクの中の領域に何が残っているかを調べません。
パーティションテーブルだけを消したディスク（`wipefs` をディスクにだけ実行した場合や、`sgdisk --zap-all` を実行した場合）では、以前のパーティションの中にあった LUKS ヘッダやファイルシステムが、そのまま残っています。
apply が同じ位置にパーティションを作ると、それらが新しいパーティションの中に現れます。

## 判断

### 操作の手段

各操作は、次のコマンドで行います。

| 操作 | コマンド |
| --- | --- |
| パーティションテーブル | `sfdisk --wipe never --wipe-partitions never`（`label: gpt`、`table-length: 128`） |
| パーティション | `sfdisk --append --wipe-partitions never`（開始位置、大きさ、種類）、`sfdisk --part-label`（ラベル） |
| LUKS | `cryptsetup luksFormat`（ADR 0009 の値をすべて明示）、`cryptsetup open` |
| PV | `pvcreate --dataalignment 1m` |
| VG | `vgcreate --physicalextentsize 4m` |
| LV | `lvcreate --size <バイト数>b --wipesignatures n --zero n` |
| ファイルシステム | `mkfs.fat`、`mkfs.ext4`、`mkfs.xfs`、`mkfs.btrfs` |
| swap | `mkswap` |
| subvolume | `btrfs subvolume create` |

パーティションの作成に sfdisk を使うのは、blkid、partx、wipefs と同じ util-linux に含まれ、追加の依存にならないためです。
ラベルは、スクリプトの中で引用符の規則に従わせないよう、引数で渡します。

各コマンドの後に `udevadm settle` を実行し、udev がデバイスを処理し終えるのを待ちます。
コマンドの標準入力は空にします。
確認を求めるコマンドは、入力を待たずに失敗します。

### 書き込む前の確認

各操作の直前に、書き込むデバイスに blkid が署名を見つけないことを確かめます。
署名が見つかった場合は、その操作を行わずに止めます。

この確認により、パーティションテーブルだけを消したディスクでは、apply はテーブルとパーティションを作った後、以前の署名が現れたパーティションに書き込む前に止まります。
以前の署名を上書きしない理由は、利用者がそれを消すつもりだったかを、apply は知りえないからです。
止まった後の組は、一部の層だけが作られた組なので、apply は拒否します（ADR 0011）。
利用者は、`destroy` で組を消去してから apply をやり直します。
このとき、`destroy` は実際にディスク上にあるパーティションの署名を消すので（ADR 0004）、以前の署名も消えます。

同じ理由で、apply が使うツールには、署名を消させません。
sfdisk には `--wipe never` と `--wipe-partitions never` を、lvcreate には `--wipesignatures n` と `--zero n` を渡します。
lvcreate は既定で LV の先頭を消すので、LV の中に残った署名は、`--zero n` がなければ確認の前に消えてしまいます。

パーティションテーブルを作る前には、ディスクが空であることを、ADR 0011 の判定で確かめ直します。

### 作った後の確認

各操作の後に、作ったものを `System` で読み直し、計画と一致することを確かめます（AGENTS.md 4 章の事後条件）。

- **パーティションテーブル**：宣言の種類の、空のテーブルがあること。
- **パーティション**：番号、開始位置、大きさ、GPT の種類、PARTLABEL が計画と等しいこと。カーネルがそのパーティションを認識していること。
- **LUKS**：LUKS2 のヘッダがあること。マッピングが開いていること。マッピングの大きさが、計画で計算した大きさ（ADR 0009 のデータの開始位置を引いた量）と等しいこと。
- **PV**：PV の署名があり、データの開始位置が 1MiB であること（ADR 0010）。
- **VG**：PE のサイズが 4MiB で、PV の集合が宣言と等しいこと。
- **LV**：大きさが計画と等しく、活性化されていること。
- **ファイルシステムと swap**：形式とラベルが宣言と等しいこと。btrfs では、すべてのデバイスが同じ UUID を持ち、マウントしてデバイスの集合とプロファイルを読んだ結果が宣言と等しいこと。
- **subvolume**：マウントした btrfs に、その `path` の subvolume があること。

一致しなければ、失敗として止めます。

### 実行の後に残す状態

LUKS のマッピングは、宣言の名前で開いたままにします。
VG と LV は、活性化したままにします。
上の層を作るために開く必要があり、閉じる理由がないからです。
再適用では、開いている LUKS と活性化された LV を通して、組を構成済みと判定できます（ADR 0015）。

btrfs は、プロファイルを確かめるときと subvolume を作るときに、`/run/diskform/<プロセス ID>` に一時的にマウントし、作業の後に外します。
マウントするときは、すべてのデバイスを `device=` で指定し、udev がデバイスをカーネルに登録したかに依存しないようにします。
apply の後に btrfs はマウントされていないので、そのまま再適用すると、データディスクの組は構成済みと判定できずに拒否されます（ADR 0015 の制約）。

### 確認の後の再検証

確認を得た後、計画を作り直し、ディスク、構成済みの組、操作が表示したものと一致することを確かめてから実行します。
一致しなければ、何も変更せずに止めます。

### 途中で失敗した場合

最初に失敗した操作で止め、完了した操作、失敗した操作、その時点の各ディスクの状態を示します。
自動で再試行も復旧もしません。
作りかけの組は apply が拒否するので（ADR 0011）、`destroy` で消去してから apply をやり直すよう示します。

## 検討した代替案

### 以前の署名を上書きする

パーティションテーブルがなければ空のディスクとして扱い、中に残った署名も上書きする案です。
`destroy` を挟まずに済みます。
しかし、ディスクを空と判定した根拠はテーブルと署名がないことだけで、中に残ったデータを利用者が消すつもりだったかは分かりません。
ADR 0004 は、既存の署名を消す操作を `destroy` に限っています。

### plan で、作る予定の領域の署名を調べる

blkid の `--offset` と `--size` で、まだ作っていないパーティションの領域を調べれば、何も書き込む前に拒否できます。
しかし、拒否した後に利用者が署名を消す手段がありません。
`destroy` は実際にあるパーティションの署名を消すので、テーブルのないディスクの中の署名は消せないからです。
apply が止まった後であれば、パーティションがあるので、`destroy` で消せます。

### sgdisk や parted でパーティションを作る

sgdisk は引数だけでパーティションを作れますが、gdisk のパッケージを追加で必要とします。
parted は、開始位置と大きさを独自に丸めることがあり、計画と一致させる確認が複雑になります。

### 作った後に LUKS を閉じ、VG を非活性化する

apply の後に、使用中のデバイスを残しません。
しかし、再適用で構成済みと判定するには、利用者が改めて開く必要があります（ADR 0011）。
開いたままにしても、`destroy` は開いている LUKS と活性化された VG を解除してから消去できます（ADR 0016）。

### btrfs をマウントしたままにする

再適用で、データディスクの組も構成済みと判定できます。
しかし、マウント先は apply の内部の一時的なディレクトリで、利用者が指定した場所ではありません。
マウントは `mount` の役割です（ADR 0004）。

## 制約

- apply の直後に再適用すると、btrfs がマウントされていないため、btrfs を持つ組は拒否されます。
  `mount` を実装する時点で、この手順を見直します（ADR 0011 の制約）。
- PV をパーティションに直接作る構成では、LV の中に以前の署名が残っていると apply が止まり、`destroy` でもその署名を消せません。
  `destroy` は PV の署名を消しますが、PV の中の LV の領域にある署名は消さないからです。
  例は PV を LUKS の上に作るので、新しい鍵で復号した領域に以前の署名は現れません。
  PV をパーティションに直接作る例が現れたら、この扱いを見直します。
- 親の subvolume が宣言にない subvolume（`a/b` だけを宣言した場合など）は、`btrfs subvolume create` が失敗します。
  subvolume は `path` の順に作るので、親が宣言にあれば先に作られます。
- `mkfs` の各ツールが行う TRIM（discard）は止めません。
  対象は apply が作ったばかりのデバイスで、書き込む前に署名がないことを確かめています。
- apply は実質的に root で実行することになります。
